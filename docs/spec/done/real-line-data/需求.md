# 真实线路数据（成都 4/6 号线）

> 跨期背景见 [`../../需求与方案.md`](../../需求与方案.md)（§7.1 数据格式、§9 里程碑 S5）。
> 本需求 = **总纲 S5「真实线路上线」的提前实施**；城市范围按用户 2026-09-28 指定：**只做 4 号线 + 6 号线**，其余线路以后再补。

## 一、要解决的问题

1. App 内线路仍是 2 条虚构示例线路（`demo1` / `demo2`），与用户实际通勤完全不符 → **无法做真实通勤实测**（M1 剩余验收项被卡住）；
2. 用户的真实通勤需要「6 号线 观东 → 玉双路」与「4 号线 玉双路 → 太升南路」两段（含换乘），示例数据无法选出来；
3. `gait-discrimination` 标定、`vibRunTh/vibStopTh` 真实车厢重标都依赖真实线路上的实测数据。

## 二、目标

1. 用**真实成都地铁数据**替换示例线路：6 号线（望丛祠 ↔ 兰家沟，56 站）、4 号线（西河 ↔ 万盛，30 站）；
2. 站名、站序与官方一致，可被 `LineRepository` 解析且不触发任何清洗丢弃；
3. 支持用户通勤两段路线选择，并保证 App 计算的停站数正确：
   - **观东 → 玉双路（6 号线，开往望丛祠方向）= 12 站**，D−1 提醒应在**牛王庙**；
   - **玉双路 → 太升南路（4 号线，开往万盛方向）= 2 站**，D−1 提醒应在**市二医院**；
4. 建立**可复核的数据生成流程**（脚本 + 回归测试），后续扩线只加数据不改流程。

## 三、非目标（明确不做）

1. **不做换乘功能**：换乘需改计数/提醒语义（算法路径），通勤实测数据回传前属红线；本次只做「单线一段」，换乘需求另立项（见 [`../active/transfer-route/需求.md`](../active/transfer-route/需求.md)）；
2. **不做全城 16 条线**：只落 4/6 号线；其余线路数据已具备（见「数据来源」），后续按同一流程扩；
3. **不引入 SQLite**：本次仍用 `assets/subway_lines.json`（决策见第六节）；
4. 不改算法路径（`core/fsm`、`core/feature`、`TuningConfig.kt`、`SensorCollector.kt`、MonitorService 监测循环），不改权限 / 通知渠道 / FGS 类型 / 包名。

## 五、ID 与命名方案

- 线路 id：`cd4`（4 号线）、`cd6`（6 号线）；线路名「4号线」「6号线」；
- 方向 id：`cd6_to_wangcongzi` / `cd6_to_lanjiagou`、`cd4_to_xihe` / `cd4_to_wansheng`；
  方向名：「开往 望丛祠 方向」等（与既有 UI 文案风格一致）；
- 站 id：`cd6_s01…cd6_s56`、`cd4_s01…cd4_s30`——**s 编号 = 该线「正向」（6 号线望丛祠→兰家沟、4 号线万盛→西河）的站序**，与用户提供数据的 order 列一一对应，便于日后核对；
- 站名不带「站」字后缀（与官方线路图一致，「中医大·省医院」「成都西站」等站名内含的「站」保留）。

## 六、存储决策：本次保持 assets JSON

用户 2026-09-28 问「线路数据为什么不用 SQLite」，结论：

- **本次保持 `assets/subway_lines.json`**（随包只读、`core` 纯 Kotlin 可 JVM 直测、git 可 diff 核对）；
- **后续迁移触发条件**：总纲 §11 #1「线路 / 站点自助管理」（App 内增删改线路 + 导入导出）立项时，数据变为「运行时可写」，届时评估迁移 SQLite；本次决策记录在案，届时不必重议。

## 八、验收标准

1. `gradlew test` 全绿（基线 66 项 + 新增资产测试，无回退）；
2. 装机后 App 内可选：线路 4/6 → 方向 → 上车站 → 目的站；观东→玉双路显示「本站起共 12 站」；
3. **真机通勤实测**（2026-09-28 早）：6 号线 观东 → 玉双路，识别站数 = 12（误差 ≤1），D−1 提醒出现在牛王庙；
4. 算法路径零改动（`git diff --stat` 自检）；通知渠道 / FGS / 包名 / 权限零改动；
5. 旧路线（示例线路）保存值失效时的行为符合预期：磁贴给出可见错误（禁止静默失败），重选路线后恢复。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 站序/站名错（影响提醒正确性，最致命） | 三源交叉核对（OSM / 官网图 / 交通卡站码）+ `SubwayDataAssetTest` 锁定关键站序与停站数（回归可拦） |
| OSM 数据含未开通站点混入 | 已按官方线路图核对 4/6 号线全部站点；4 号线 30 / 6 号线 56 与官网站数一致 |
| 旧路线失效导致磁贴报错 | 已知行为（可见报错，不静默）；文档与交接注明「装机后需重选路线一次」 |
| 56 站下拉菜单掉帧回退 | `LazyColumn` 定点优化（ui-jank-diagnosis 结论：菜单成本在组合/首绘，与项数无关，但大列表仍需懒加载） |
| 数据源为第三方（OSM）非官方 API | 站点名与站序已双源核对；日后官方开放数据接口时可替换，流程不变 |
