# Wi-Fi 指纹采集器重扫风暴修复（wifi-collector-fix）

> 从 [`cellular-wifi-fingerprint-validate`](../cellular-wifi-fingerprint-validate/需求.md) 第八节裁决派生的采集器缺陷修复需求（lab 旁路，不碰主链路）。
> 修复后下一趟通勤重测，H1/H2/H4 才能补裁决。

## 一、缺陷实录（2026-09-29 早通勤 `lab_20260929_080458`，39 min）

| 指标 | 实测值 |
|---|---|
| `WIFI_STARTSCAN_FAIL` | **653,435 条**（≈279 条/s） |
| `WIFI_SCAN_ERROR` | **653,049 条** |
| `lab_events.csv` 体积 | **71.6 MB**（占整个 lab 目录的 64%） |
| `lab_wifi.csv` 数据 | 2410 行快照**全部为空**（ap_count=0 / direct_count=0） |
| App 主动扫描成功率 | **0%**（每次 `startScan()` 均被系统拒绝） |

## 二、根因

`LabWifiCollector` 在**每次扫描广播回调里立即续扫**（原注释「收到结果立即续扫」）。HyperOS 拒绝
`startScan()` 时仍会发出 `SCAN_RESULTS_AVAILABLE_ACTION`（`EXTRA_RESULTS_UPDATED=false`）→
失败 → 回调 → 再请求 → 再失败的**热循环**（实测 ≈280 次/s）。两处放大：

1. 每次请求失败 + 每次扫描失败各落一条事件，**事件无节流** → 每秒 ~558 条、71.6 MB；
2. 每秒数百次的重扫风暴疑似触发 HyperOS **持续限频自锁**——整趟 0 次成功，`getScanResults()`
   缓存也为空，H1/H2/H4 全部断粮（环境信号存在：用户前晚系统 Wi-Fi 列表可见 `DIRECT-` 信标、今早高德可站级定位）。

## 三、修复方案（2026-09-29 已实施）

- **30 s 固定节拍器**：`Handler(Looper.getMainLooper())` 每 30 s 发起一次 `startScan()`
  （`MIN_RESCAN_INTERVAL_MS=30_000`）——后台限频（4 次/2 min）量级下仍保证每站间区间 ≥3 次尝试（H4 通过标准）；
- **回调不再续扫**：广播回调只写快照（1 Hz 节流不变）与失败证据，节奏统一由节拍器驱动——热循环在结构上不可能再现；
- **失败事件 60 s 节流**（`FAIL_EVENT_THROTTLE_MS=60_000`）：`WIFI_STARTSCAN_FAIL` /
  `WIFI_SCAN_ERROR` 保留**累计计数**（`count=N`），节流窗口内的失败静默——不刷屏也不掩盖总量；
- 决策抽纯函数并回归：`shouldRequestScan` / `shouldWriteFailEvent`（`LabWifiCellCollectorsTest` 新增 2 项）。

## 四、验收标准

1. `gradlew test` 全绿（107 项，105 基线不回退）+ `:app:assembleDebug` 通过；✅ 2026-09-29 已通过；
2. 装机后**今晚通勤（2026-09-29 晚）重测**：
   - `lab_events.csv` 无风暴：全程 Wi-Fi 失败事件 **≤ 100 条**（30 s 节拍 × 60 s 节流的理论上限 ≈ 78 条）；
   - `lab_wifi.csv` 出现**非空快照**（ap_count > 0 的行数 > 0）；
   - 每站间区间的快照数可统计 → 作为 H1/H2/H4 补裁决的取数；
   - 若仍 0 非空快照：记录 `WIFI_START` 事件与失败计数，评估 `setScanAlwaysAvailable` / 前台保活 / 系统限频白名单等替代通路（升级为本需求第二节遗留项）。
