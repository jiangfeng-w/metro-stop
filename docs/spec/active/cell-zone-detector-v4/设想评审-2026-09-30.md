## 二、② rssi 判停动 —— 否定

### 原设想

> 「一路监控信号变化，看是不是列车到站停下后，信号强度是不是就不变了，列车启动后信号又开始变化」

### 更正为

**rssi 不能用于判定「停稳 / 启动」。** 该信号在停稳期间本身就在剧烈波动，且采样率不足以刻画秒级的停动事件。
rssi 的价值应改挂在**站内 vs 隧道的分布特征**上（不依赖时间分辨率），判停动仍归 IMU。

### 依据（2026-09-29 早通勤 6 号线 12 站；cells 流 328 行 / sensor 流 89,496 行）

**(1) 采样率就不够 —— 0.2 Hz 级**

| 指标 | 实测 |
|---|---|
| 中位采样间隔 | **5.00 s**（cd4 段 4.72 s）→ 约 0.2 Hz |
| 平均间隔 | 5.76 s |
| p90 间隔 | 11.28 s |
| 最大间隔 | **24.1 s** |
| 间隔 > 10 s 占比 | 11.3% |
| 间隔 > 20 s 占比 | 3.1% |

「停下 / 启动」是秒级事件，8 s 判定窗内只有 1~2 个采样点，**时序结构根本建不起来**。
（注：`CellMonitorCollector.kt:17` 注释写的是「1 Hz 节流」，但节流是**上限**不是**保证**——
实际出流由回调触发时刻决定，实测就是 5 s 一档。）

**(2) 停稳期间 rssi 照样在摆 —— 摆幅大于任何想用的判决量**

| 分组（按 sensor 流 `state` 标签） | 样本 | rssi 范围 | 跨度 | 标准差 | 相邻差分 中位 / 均值 |
|---|---|---|---|---|---|
| STOPPED（停稳） | 142 | −99 ~ −66 | 33 dB | 6.38 dB | **3 / 4.8 dB** |
| CRUISE（行驶） | 181 | −137 ~ −52 | 85 dB | 8.68 dB | **4 / 5.6 dB** |

**「停稳」与「行驶」的相邻差分只差 0.8 dB，而停稳期自身的摆幅中位 13 dB。**

更强的一条：**「停稳 + 同一服务小区」的连续段共 19 段**（列车停着不动、门开着、小区都没换），
rssi **摆幅中位 13 dB、均值 12.5 dB、最大 22 dB**，段内标准差中位 4.23 dB / 最大 7.32 dB。
（放宽到"任意状态 + 同一服务小区"的 31 段：摆幅中位 14 dB、最大 59 dB。）

> 与 `需求.md` 第十节的现场初挖互相印证：市二医院停稳窗中位 −80 dB vs 太升南路 −84 dB，
> **中位差只有 4 dB**，而停稳窗内自身摆动 ±10 dB 以上 —— 单趟不可分的原因就在这里。

**(3) 物理上限：快衰落速率远高于采样率**

| 频段 | 波长 λ | 半波长相干距离 λ/2 | 60 km/h（16.7 m/s）穿过时的衰落零点速率 |
|---|---|---|---|
| 2.6 GHz（Band 41） | 11.5 cm | 5.8 cm | **≈ 289 个/秒** |
| 1.8 GHz（Band 3） | 16.7 cm | 8.3 cm | **≈ 200 个/秒** |

漏缆的辐射点相对地面固定，列车是**穿过**一个静止的驻波干涉图样 → 时域衰落速率 = v/(λ/2)。
**这是采样率层面的硬约束，不是调参能救的**（5 s 采样对 200~290 Hz 的衰落，混叠比千倍以上）。

**(4) 换一个更准确的对比（更正讨论中的一处口头表述）**

判定「停动」的真正依据**不是单样本幅度对比度，而是时间分辨率 + 时序结构**：

| | IMU（`vib`） | 蜂窝（`rssi`） |
|---|---|---|
| 采样间隔 | **21 ms** | 中位 **5.0 s**（p90 11.3 s） |
| 相对时间分辨率 | **1×** | **慢 238×** |
| 单样本分布 | CRUISE 中位 0.147 vs STOPPED 中位 **0.122** —— **高度重叠** | 噪声 13 dB |
| 判别量 | `vib < 0.085` 占比：STOPPED 28.6% / CRUISE 16.4% | STOPPED vs CRUISE 差分差 0.8 dB |
| 判定依赖的结构 | **≥8 s 持续静稳跨度**：STOPPED 7 段（最长 30.4 s）vs CRUISE 2 段（最长 12.2 s） | 8 s 窗内仅 1~2 个点，结构不可建 |

**更正后的表述**：IMU 的优势不是"信号更强/对比度更高"，而是**快 238 倍的时间分辨率，使判定可以建立在
「持续静稳跨度」这类时序结构上**。这一条同时解释了 v4 的存在理由——IMU 单样本分布重叠、区间信号停车仍会误报
（`需求.md` 第一节：晨高峰 5 站漏检 + 3 次信号停车误计，按键 9 次），所以必须再叠一层蜂窝分区做身份约束。
（仓库注释 `StationStopDetector.kt:463-466` 已记录同类结论：站姿乘车与站台静立在 vib / gyro 分布上几乎同分布。）

> ⚠️ **口径修正**：本次讨论过程中一度出现「IMU 振动是清晰方波、对比度约 20 倍」的说法，**经复核不成立**——
> 该数字来自 2026-09-25 的早期回放资产（那时 `vib` 量纲与现版本不同，`real_journey_3stops_20260925.csv`
> 的 CRUISE 中位 7.32，现版本为 0.147）。**以本文表格为准。**

**(5) 更正后 rssi 该用在哪里**

| 用途 | 结论 |
|---|---|
| 判停动 | ❌ 放弃 |
| **站内（室分）vs 隧道（漏缆）的分布特征** | ✅ 值得挖——两类覆盖的 rssi 统计差异是**结构性**的，不依赖时间分辨率 |
| 共享区（701 区）两站拆分 | ⚠️ 可用，但优先级低于 TA（见 `架构评审` P1-c） |
| 沿线行进进度 | ⚠️ 兴趣向，暂不碰 |

> 与 `需求.md` 第十节方向一致，只是把**目标从"判停动"换成"覆盖形态特征"**。

## 三、③ 邻区 / 多小区 —— 整句更正

### 原设想

> 「一般来说一段区域的 cell id 不可能只有一个吧，一般会有多个，只不过我们只用了主 cell id」

### 更正为

**同一时刻只有 1 个（99.7% 的快照），整段行程平均每站约 2.7 个。** 因此正确的技术路线是
**序列级解码（HMM / Viterbi）**，而不是「同一时刻的邻区集合指纹」——后者要求同一时刻存在多个小区，现场不具备。
同时更正一处代码事实：**邻区不是"没用"，而是"没有邻区可采"**。

### 依据

**(1) 时刻维度 vs 行程维度**

| 维度 | 实测（cd6 早通勤 1885 s / 12 站） |
|---|---|
| 每快照小区数（时刻维度） | 中位 **1**、最大 **2**；**==1 占 99.7%**、==2 占 0.3% |
| 全部小区流资产合计（397 行，cd6 + cd4） | 中位 1、最大 2、**99.7% 单小区** |
| 不同 `pci:ci` 总数（行程维度） | **32** 个 |
| 主服务小区切换次数 | **40** 次 |
| 折算 | **≈ 2.7 个小区 / 站** |

即：**一个小区覆盖一段区间** —— 隧道漏缆线性覆盖的必然结果，不是采集缺陷。
（`cd4` 段更极端：69 行**全部**为单小区、5 个不同小区 / 2 站。）

**(2) 邻区在代码里的真实状态（更正"只用了主 cell"这一判断）**

邻区**已经**贯穿采集与判定链路：

| 环节 | 位置 | 作用 |
|---|---|---|
| 采集归一化 | `LabCellCollector.parseCells()` | 保留**全部**小区（不只主服务） |
| 序列化 | `LabCellCollector.formatCells()` | 全量写入 `pci:ci:rssi`，`\|` 分隔 |
| 主/邻拆分 | `CellMonitorCollector.kt:74-75` | `ids.firstOrNull()` 主服务 / `ids.drop(1)` 邻区 |
| **邻区兜底匹配** | `CellZoneTracker.kt:90` | `byCell(mainCell) ?: neighbors.firstNotNullOfOrNull { byCell(it) }` |

也就是说：**代码早就为邻区留好了位置，但实测邻区 99.7% 为空，这条兜底分支在实战中从未被触发**
（= 事实上的死代码）。

> 邻区恒空是**权限导致**（Android 10+ 无 `ACCESS_FINE_LOCATION` 时只回服务小区）还是**物理覆盖导致**，
> 可用 lab 的 `cellid` 流（具备定位权限）对比每快照小区数定论；本评审倾向物理原因
> （漏缆线性覆盖 + 站区单小区规划）。**这是一个待确认项，不影响本文结论。**

**(3) 更正后的技术路线**

| | 原设想的隐含路线 | 更正后 |
|---|---|---|
| 判据形态 | 「当前可见小区集合」的指纹匹配 | **序列级解码**：观测 = 逐拍可见小区，状态 = 站位 |
| 推荐算法 | （未明确） | **HMM + Viterbi**：转移只能前进 + 站间运行时长先验 |
| 能解的遗留问题 | 单点漂移 | ① 701 共享区两站消歧 ② 919↔708 乒乓 ③ 单点漂移（琉璃场 780→879、陆肖 ci 一字之差、市二医院 701→820）④ 断档外推 |
| 副产品 | — | 「观测序列总似然低于阈值」→ 直接实现 `需求.md` 风险表里的**「提示重学」** |

**关键认知**：「一个小区覆盖相邻两站」是蜂窝规划的必然（站台与隧道同小区以避免切换集中 + 漏缆 500 m 断点布放），
**不是映射 bug，学得更准也解决不了**。序列级解码正是把这一点从"缺陷"转成"先验"。

## 四、① 双卡交叉学习 —— 方向对、入口错

### 原设想

> 「采集 cell id 同时采集两张手机卡的信号，做交叉学习」

### 更正为

**方向成立，但第一步不是交叉学习，而是先把键空间修对**：

1. 映射键与节流签名从 `pci:ci` 升级为 **`mcc:mnc:pci:ci`**（即 `调研报告` 3.1 节已提到的 CGI 形态）；
2. 快照增加 **卡槽（simSlot）** 字段，主/邻区拆分按卡分别处理。

**完成这两步之后**，交叉学习才有意义，且收益点是**异网交叉**（见下）。

### 依据

**(1) 当前实现的三处缺口**

| 事实 | 位置 | 后果 |
|---|---|---|
| `CellSnapshot(pci, ci, rssi, registered)` —— **无 MCC/MNC** | `LabCellCollector.kt:89` | 键空间是 `pci:ci`，而 **pci 只有 0~503、跨运营商复用** → 不同运营商可能撞进同一映射键 |
| `sortedCells = snaps.sortedByDescending { it.registered }` | `LabCellCollector.kt:104-105` | 双卡双待时**两张卡都 `isRegistered=true`**，排序后退化为"系统给的顺序" |
| `ids.firstOrNull()` / `ids.drop(1)` | `CellMonitorCollector.kt:74-75` | 排序后第一张卡的当前小区成为"主服务"，**第二张卡的当前小区被塞进 `neighbors`** —— 语义错位 |

**(2) 异网交叉的真实收益**

「站台与隧道划为同一小区」是**单个运营商的规划决策**——移动 / 联通 / 电信的小区边界不会重合。
用两张卡换一份额外的**空间区分度**，这正是 701 共享区拆分最缺的东西，属于低成本高回报。

**(3) 两个必须先确认的前提**

| 前提 | 若不满足 |
|---|---|
| **两张卡是否异网？** | 若同为移动，两卡在同一基站下看到的小区基本一致，**收益 ≈ 0** |
| **副卡是否常驻 2G？** | GSM 无 PCI（`idOrUnknown` 填 **−1**），同一小区所有样本同键，粒度更粗，需单独处理 |

## 五、④ 服务端闭环 —— 架构直觉对、四处要改

### 原设想

> 「感应到有定位卫星信号的时候，就说明出了地铁站，此时自动把采集的数据上传到服务器（或者闲时上传），
> 等我自己到家之后再用 AI 从服务器拉取数据并对其进行分析，然后通过服务器把映射后的站点和 cell id
> 下发到手机数据库」

### 更正为（四处）

| # | 更正前 | **更正后** |
|---|---|---|
| 1 | 触发条件 = **GNSS 恢复** | 触发条件 = **网络可用**；实际优选 **连上 Wi-Fi / 充电中** |
| 2 | 「用 **AI** 分析」 | 实质是**序列对齐（DTW / Viterbi 全局对齐）**，不是 LLM |
| 3 | 映射文件直接下发即可 | 需先做 **运行时可写存储 + 版本号 + 校验 + 回滚 + 与内置版合并** |
| 4 | （未提及）纠错回传 | **必须补上**，否则是单向通道，映射错误只累积不修正 |

**结论层面：把重活放服务端是正确的**——全局优化正适合离线跑，手机端只跑轻量匹配。

### 依据

**(1) 触发条件写错了：隧道里**有**蜂窝网**

`CellInfo` 本身就是蜂窝网提供的——**没有网就没有小区数据，v4 整条主通道都不成立**。
所以「出站才有网」与现实相反。更稳的上传触发：**连接 Wi-Fi / 充电中**（零额外权限、零流量顾虑）。
反过来说，「GNSS 恢复 = 出站」还会**误触发**（隧道口、U 型槽、靠出口的地面/高架站台）。

**(2) 全仓库目前没有任何网络代码 —— 服务器要从零建**

已核实：`app/src/main/java` 下**无 OkHttp / HttpURLConnection / Retrofit / 任何 URL**。
纠错事件 `CORRECTION_UP` / `CORRECTION_DOWN`（`MonitorSession.kt:471/523`）**只落本地会话流**，
不会离开设备 → 现状是**单向通道**：服务端只能收，收不到"哪一站的映射错了"。

**(3) 下发映射有一笔没算进去的架构成本**

`cell_zones.json` 现在由 `MonitorService.kt:274` 从 **assets 只读加载、随 APK 打包**
（git 里靠人工改 + 重新发版，当前还是 `M` 状态）。要支持服务端下发，必须新建：

运行时可写存储 → 版本号 → 校验和 → 回滚 → **与内置版合并策略**（内置版继续做冷启动兜底）。

好消息：可搭 `trip-history-db` 那条 SQLite 车道，不必另起一套。

## 六、结论：先别建服务器

| 判断 | 说明 |
|---|---|
| 想验证的两件事，**仓库里的回放资产已经能判** | ①rssi 停站稳不稳 ②邻区够不够用 —— 本文**一行 app 代码未改**，纯读 replay 数据即出结论 |
| 服务器解决的是**下一步**的问题 | 多趟聚合 + 全局优化 + 多设备下发 |
| 在假设验完之前建服务器 = **给未验证的东西上基础设施** | 建议按下方顺序推进 |

### 建议顺序（前四项均不需要服务器）

| 序 | 事项 | 成本 | 说明 |
|---|---|---|---|
| P0-1 | 定位权限与规则表述修正 | 低 | 见 `架构评审-2026-09-30.md` 第二节（地基性风险） |
| P0-2 | 主动驱动 `requestCellInfoUpdate()` | 低 | 解 10~20 s 断档；`getAllCellInfo()` 在 Q+ 只返缓存，**轮询治不了** |
| P1-a | **MCC/MNC + 卡槽**（本文第四节） | 半天 | 解锁双卡与运营商分片，是双卡交叉学习的**前置** |
| P1-b | rssi 挖**新目标**（站内 vs 隧道分布特征 / 共享区拆分）+ **TA 同批采集** | 半天 | TA = `CellSignalStrengthLte.getTimingAdvance()`，≈78 m/格，单调稳定，无需新权限 |
| P1-c | **序列级解码（HMM + Viterbi）** | 中 | 一次消解四个遗留问题（见第三节） |
| P2 | 服务端闭环 | 高 | 等前四项结论；若要提前动手，先只做 **纠错回传**（成本最低、收益最直接） |

# C. IMU 判别力：静稳占比 + 持续静稳跨度（TH=0.085, tol=2s）
python - <<'EOF'
import csv, statistics
rows=sorted((int(x['t_ms']), float(x['vib']), x['state'])
            for x in csv.DictReader(open("real_commute_cd6_12stops_morning_20260929.csv",encoding='utf-8-sig')))
def spans(sub, tol=2000, th=0.085):
    out=[];start=None;last=None
    for t,v,_ in sub:
        if v<th:
            if start is None: start=t
            last=t
        elif start is not None and t-last>tol:
            out.append((last-start)/1000.0); start=None
    if start is not None: out.append((last-start)/1000.0)
    return sorted(out,reverse=True)
for lab in ("STOPPED","CRUISE"):
    sub=[r for r in rows if r[2]==lab]
    sp=spans(sub)
    print("%-8s n=%d P(vib<0.085)=%.1f%% spans>=8s=%d max=%.1fs" % (
        lab,len(sub),100*sum(1 for r in sub if r[1]<0.085)/len(sub),
        sum(1 for x in sp if x>=8), sp[0] if sp else 0))
EOF
