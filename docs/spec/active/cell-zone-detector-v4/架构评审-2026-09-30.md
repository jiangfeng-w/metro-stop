## 一、总体判定

**方向正确，且已被数据验证。** v4「蜂窝分区主导 + IMU 定时刻」与业界（高德/百度）和学术界（SubTrack）
在同类问题上收敛到的架构**同构**——这一点值得明确记录下来，因为它是你的方案不是空中楼阁的证据。

| 独立调研结论 | 你的项目实测/实现 | 一致性 |
|---|---|---|

## 二、P0 地基性风险：定位权限耦合（会导致方案整体打穿）

### 问题

`AndroidManifest.xml` 中：

```xml
<!-- 下面三行是 lab-data-collection（短期调试数据采集）的临时例外，
     仅供实验室采集旁路服务使用，主功能不申请不读取；采集需求下线时一并移除： -->
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
```

同时 `docs/README.md` 的待办里明确写着 lab 需求「待办：需求正式下线（UI 移除 + **权限回收**）」；
`AGENTS.md` 硬性规则 3 写「**不申请定位权限**」。

**但这三条互相冲突，且冲突会打穿 v4：**

**Android 10（API 29）起，读取 `CellInfo` 被归类为「精确定位数据源」，官方强制要求
`ACCESS_FINE_LOCATION`** —— `TelephonyManager.getAllCellInfo()` 的契约注解即
`@RequiresPermission(ACCESS_FINE_LOCATION)`，`LISTEN_CELL_INFO` / `TelephonyCallback.CellInfoListener` 同理。

也就是说：

- 主链路小区流现在**能跑通，是因为 lab 的 `ACCESS_FINE_LOCATION` 恰好还在 manifest 里**；
- 一旦按计划执行「lab 下线 → 权限回收」，**`CellMonitorCollector` 与 `LabCellCollector` 会同时拿不到数据**
  → v4 的分区通道整体失效 → 只能回退 v3（而 v3 已裁决触顶）；
- 这是**一条隐式依赖**，当前 `AGENTS.md` / `进度与交接.md` / v4 需求文档**均未识别**。

### 处置建议

1. **把 `ACCESS_FINE_LOCATION` 从「lab 临时例外」升级为「主链路必需权限」**，与 `READ_PHONE_STATE` 并列写进
   v4 需求 2.4 节与 `AGENTS.md` 规则 3；
2. **改写硬性规则 3 的表述**（当前表述会误导后来的接手者按注释删权限）。建议改为：

   > **不引入任何定位 / 地图 / 第三方位置 SDK，不读取任何坐标。**
   > 蜂窝标识（CellInfo）在 Android 10+ 被平台归类为精确定位数据源，因此需声明
   > `ACCESS_FINE_LOCATION`；该权限**仅用于通过平台校验以读取小区标识**，代码中不得出现任何
   > 坐标读取（LocationManager / FusedLocation / `CellIdentity.getLatitude()` 等）。

3. **加一条自检**：在 core 或测试中锁定「除 `platform/cell/` 与 `platform/lab/` 外，
   不得出现任何 `android.location.*` / `getLatitude` 引用」——把这条隐性依赖变成可回归的约束。
4. `ACCESS_COARSE_LOCATION` 可评估移除（lab `loc` 流用得到，随 lab 一起下线即可）。

> ⚠️ 顺带说明：这条建议与「定位不可用」的既有裁决**不矛盾**。隧道内 GNSS 全灭、network 档 500 m 冻结
> 的结论依然成立——**我们不是用它来定位，而是用它来通过平台的权限校验读小区标识**。两者是两件事。

## 三、P0 性能/精度：小区流拍点稀疏的根因与修法

### 现状

`docs` 里记录了两条强相关的遗留问题：

- 「主链路小区流 **146 处 10~20 s 断档**」；
- 「到站时刻双向漂移 −33.8~+32.6 s」，用户体感「比高德慢」。

**根因在 `CellMonitorCollector` 的数据源设计**：

```kotlin
val l = object : PhoneStateListener() {
    override fun onCellInfoChanged(cellInfo: MutableList<CellInfo>?) { onCells(...) }
}
tm.listen(l, PhoneStateListener.LISTEN_CELL_INFO)
onCells(tm.allCellInfo.orEmpty())   // 仅此一次首拍
```

**全部数据只来自被动回调 + 启动首拍，没有任何主动拉取驱动。**

而 Android Q 起有一条关键行为变更（官方原文）：

> "Apps targeting Android Q or higher will no longer trigger a refresh of the cached CellInfo by
> invoking this API. Instead, those apps will receive the latest cached results, which may not be
> current. Apps targeting Q or higher that wish to request updated CellInfo should call
> `requestCellInfoUpdate()`; however, in all cases, updates will be rate-limited and are not guaranteed."

两个后果：

1. **`onCellInfoChanged` 的触发时刻由系统缓存刷新决定**，不是每秒一次 → 这就是 10~20 s 断档；
2. **靠 1 Hz 轮询 `allCellInfo` 也救不了**——Q+ 上它只返回缓存、不再触发刷新（这是最容易被误判为
   「加个定时器就行」的陷阱）。

而高德的「跳站」本质上就是**小区切换事件本身**。你的流断了 10~20 s，位置更新自然滞后 —— 这就是
「比高德慢」的机制性根因，不是调参能解决的。

### 修法（按收益/成本排序）

| # | 动作 | 说明 | 成本 |
|---|---|---|---|
| 1 | **引入 `TelephonyManager.requestCellInfoUpdate()` 主动刷新驱动** | Q+ 官方指定的主动刷新 API；带 `CellInfoCallback`；**API 30+，需版本守卫**（minSdk 26 要兜底走现有路径）；必须处理 `ERROR_RATE_LIMITED` 并允许失败 | 中 |
| 2 | **迁移到 `TelephonyCallback`** | `PhoneStateListener` 自 API 31 起废弃，正道是 `registerTelephonyCallback(executor, TelephonyCallback.CellInfoListener)`。附带收益：绕开 OEM 对旧 `listen()` 的兼容层——你已经在 HyperOS 的 `WifiManager` 兼容层上踩过完全同源的坑，风险不容忽视 | 小 |
| 3 | **「变化即写」判据拆分** | 见下 | 小 |

### 附带发现：`shouldWrite` 的签名语义与注释不符

```kotlin
fun formatCells(snaps) = snaps.joinToString("|") { "${it.pci}:${it.ci}:${it.rssi}" }
fun cellsSignature(snaps) = formatCells(snaps)          // ← 签名含 rssi
fun shouldWrite(now, last, sig, lastSig) = sig != lastSig || now - last >= 1000L
```

注释写的是「小区集合签名变化立即落行（**切换**不落节流窗）」，但实现上
**`rssi` 抖 1 dB 就算「签名变化」→ 立即写行**。后果：

- 写入密度不可控（rssi 高频波动时可能远高于 1 Hz），落盘体积与节流语义都失真；
- 「断档」统计口径也不干净——10~20 s 无行意味着 **rssi 也完全没变**，这反过来更说明是
  **回调根本没触发**（隧道内 rssi 不可能长时间恒定），进一步印证上面的根因判断。

**建议**：拆成两个签名——`identitySignature`（仅 `pci:ci`，用于「切换立即写」）与完整行（含 rssi，
用于落盘内容）。语义清晰、密度可控，调研/挖掘时的「数据缺口」指标才可信。

## 四、P1 算法升级：从「逐站独立硬匹配」到「序列级概率解码」

### 现状与证据

`CellZoneTracker.resolve()` 使用的是**硬集合匹配**：

```kotlin
private fun zoneOf(stations, cell): IntRange? {
    // st.cells.contains(cell)  —— 0/1 判定，单点差异零容忍
}
```

而你的数据已经反复暴露**站台扇区隔天漂移**（rideCount=1 映射泛化不足的三例）：

| 站 | 映射学到的 | 当晚/次日真值 | 后果 |
|---|---|---|---|
| 琉璃场 | `780` | `879` | 站区门 4 连拦真候选 |
| 陆肖 | `807:…7578` | `807:…7538` | **ci 一字之差**，匹配失败 |
| 市二医院 | `701` | `820` | 站区门拦真实候选 |

**这不是「多学几趟就好」的问题。** 单点硬匹配对这类漂移结构性地零容忍——一处失配整站漏判。

### 建议：在现有架构内升级为序列级解码

保持所有既有工程约束不变（纯 Kotlin / CSV 可回放 / 调参闭环 / 判定与资产分离），只把
「逐拍独立判定」换成「在线路站位序列上的最优路径解码」：

1. **资产结构升级**：`station → Set<cell>` 改为 `(station, cell) → 权重`（出现率或共现次数）。
   现有的 `confidence` 字段正好承接。
2. **观测**：每拍可见的小区集合（主服务 + 邻区，用上现有的 `ids` / 邻区列表）。
3. **解码**：HMM + Viterbi
   - 状态 = 线路站位 1..k；
   - 转移 = 只能前进或小幅回退（列车不跳站，除甩站）；
   - 发射概率 = 观测集合对 `(station, cells)` 的似然；
   - **转移时长用站间运行时长先验**——这个先验你已经在免费积累了（`minStopIntervalSec=60`
     就是它的雏形，实测站间 100~201 s 是它的完整形态）。
4. **副产品**：输出「本次观测序列对映射的总似然」→ **低于阈值即告警「映射可能漂移，需重学」**，
   直接落地你「风险与对策」表里那条「超阈值提示重学」，不用另做机制。

### 为什么这值得优先做：它一次性消解你当前四个遗留问题

| 现有遗留问题 | Viterbi 如何消解 |
|---|---|
| **701 共享区覆盖两站**（D−1/到达连锁提前 60~79 s） | 共享区给出两个候选站位 → 由「只能前进 + IMU 停稳时刻」消歧，**不必依赖 rssi 硬拆** |
| **顺江路~牛王庙小区乒乓**（919↔708） | 观测噪声由序列一致性平滑；现在是靠「邻区兜底」逐拍救，脆弱且无状态 |
| **映射单点漂移**（780→879 / ci 一字之差） | 邻区集合相似度给次优候选，序列一致性救回；不再要求精确命中 |
| **断档 10~20 s** | 无观测时段靠转移模型外推，不再等价于「位置未知」 |

> **关键认知**：`701 区一段覆盖两站` **不是映射 bug，是蜂窝规划的必然结果**。
> 地铁工程的通行分区原则是「站台与站厅不同小区覆盖以保证容量；**站台与隧道划为同一小区以避免切换集中出现**」，
> 漏缆还按约 500 m 断点布放设备。所以「一个小区覆盖相邻两站」在工程上是预期行为。
> → **不要指望通过「把映射学得更准」解决它**，只能靠更细的信号（rssi / TA）或更强的先验（序列 + IMU 时刻）。
> 这条建议同时适用于你按方向独立建映射的策略：方向差异（上下行覆盖不同）确实存在，但共享区是另一回事。

**验证方式**：完全离线，用已入库的 `app/src/test/resources/replay/` 资产跑，不需要新的通勤采集。
符合你 `docs/` 里「先取证再改」的既有纪律。建议**与 rssi 挖掘并行**，而不是排在它之后。

## 五、P1 采集：TA 应立刻采，且优先于 rssi

你在 v4 需求第十节把 **LTE TA（Timing Advance）** 列为「彩蛋，未采集」。评审意见：
**它应该是一等公民，且优先级高于 rssi。**

| 维度 | rssi（你正在挖） | TA（未采） |
|---|---|---|
| 物理量 | 接收功率（强度代理） | 传播时延（**距离代理**） |
| 漏缆场景噪声 | **大**——你实测区间段 −71~−90 dBm 大幅跳动（多径/车体/朝向） | 小——时延量物理单调 |
| 与「距离」的关系 | 间接、非线性、受环境影响 | **近似线性**，一步 ≈78 m 单程（3GPP：TA 步长 16·Ts，往返 ≈156 m） |
| 可用 API | 已有（`dbm`） | `CellSignalStrengthLte.getTimingAdvance()`——**就在你已解析的 `CellInfoLte` 上，无需新权限** |
| 落地成本 | 0（已在采） | 半天：`parseCells` LTE 分支多取一字段 + 行格式 `pci:ci:rssi` → `pci:ci:rssi:ta` |

**直接收益**：

1. **701 共享区拆分**（你当前最优先用途）——TA 随列车前进递增，两站的 TA 区间大概率天然可分，
   比 rssi 中位差 4 dB 的边际信号可靠得多；
2. **进区提前量收紧**（缓解 D−1 文案错位）；
3. **「区间进度条」**——你标为「兴趣向、暂不碰」的功能，TA 是唯一现实的实现路径
   （漏缆沿线时延近似线性）。

**注意**：
- NR 在 Android 上无公开 TA API（`CellSignalStrengthNr` 无对应方法）→ **只能采 LTE 锚点**，
  但你数据里主服务就是 LTE，够用；
- `getTimingAdvance()` 的取值单位需**实测标定**（不同实现可能给 16Ts 计数或已换算值），
  建议用两站已知间距做一次标定写入 `TuningConfig` 注释；
- 建议**和 rssi 挖掘同一次采集做掉**，一次通勤同时拿两个量，边际成本为零。

## 六、P2 若干（非阻塞，按需处理）

### 6.1 K80 无气压计 → 「开门事件」这条最强独立证据链当前不可用

`SENSORS_MISSING: baro` —— 你的设备没有气压计。

而本领域**最贴近的技术终点**（专利 **CN111222836A**《一种到站提醒方法及相关装置》）的核心手段，正是
**气压计开门/关门特征向量（滑动窗 → 3TF 维向量 → 聚类中心 + 聚类半径）+ 定位区域双重判定**。
它测的不是高度差，而是**开门瞬间车厢内的气压扰动波形**。

值得记录的原因：它恰好是你现在最痛的两个问题的**通用解**——
「到站 vs 区间信号停车」（信号停车不开门）与「共享区两站」（不需要区分小区）。

**当前设备无解，建议归档到总纲「后续优化」，换机时作为与蜂窝并列的一等信号启用。**
顺带：该专利在背景技术中**同时否定了纯 Cell ID 与「Cell ID + 加速度」两类现有方案**（理由正是
「用户移动手机和列车变轨抖动」，与你 2026-09-27 误报事故的根因描述一致）——把你的方案演进史与之一对，
会发现你走的是同一逻辑顺序，只是把「气压计」换成了「IMU 静稳 + 蜂窝分区」。

### 6.2 IMU 状态显示错乱 —— 建议抽纯函数

```kotlin
snapshot() → MonitorUiState(state = detector.state, zoneStation = zoneTracker.confirmedRange?...)
```

两个独立状态机各自抖动，拼装规则既没有单一真源也没有测试覆盖，这是「运行显停稳 / 停稳显巡航」的结构性来源。

**建议**：新增纯函数 `displayState(imuState, zoneRange, expectedPosition): DisplayState` 放在 `core/`，
并配单测。抽出来后这类问题会被测试直接锁死，而不是靠现场观察发现。

## 七、后续优化优先级建议

排序原则：**先堵会打穿方案的地基性风险 → 再做能在现有数据上离线验证的算法升级 → 最后才是新传感器/新采集。**

| 优先级 | 事项 | 类型 | 依赖 | 备注 |
|---|---|---|---|---|

## 九、一句话总结

**方案选型是对的，工程纪律（纯 core + CSV 回放 + 资产分离 + 降级链 + 调参闭环）是这个项目最大的资产，
不要动它。** 需要做的是：**堵住定位权限这个隐式依赖（P0），把「逐站硬匹配」升级为「序列级解码」（P1），
并补上 TA 这个被低估的距离量（P1）** —— 三件事都不需要推翻任何既有设计。
