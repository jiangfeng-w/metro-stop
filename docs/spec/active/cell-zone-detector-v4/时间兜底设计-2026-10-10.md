# 「时间兜底」提前提醒设计（初稿，2026-10-10）

> 状态：**设计初稿，待用户拍板后实施**（判定路径改动，需全量回归 + `install -r`）。
> 来源：用户 2026-10-09 口径（「宁早勿晚」）与 2026-10-10 C1 首验日发现（App 后台蜂窝数据不可得）。
> 关联：`需求.md` §六风险表「息屏/后台空样本」行、仓库外 `analysis/FINDINGS-2026-10-10.md` §7。

## 一、动机（为什么需要不依赖蜂窝的通道）

- 用户核心需求 = **接近目的站时提前提醒准备下车**；口径「提前几十秒/半分钟可接受、早发无害，**晚于停稳（车门打开）不可接受**」。
- 现状两级提前提醒（D−1 / 即将到达）都依赖蜂窝站区；App 后台时蜂窝数据不可得（2026-10-10 实测：空行率 51~86%，仅用户与手机交互前后的短窗有值）。→ **后台场景提前提醒全灭、只剩 IMU 停稳兜底（= 用户体感「开门才提醒」）**。
- IMU 通道（50 Hz 零断档）虽能计数，但「到站时刻」精度有限（±40 s 级）；**时间先验**是唯一不依赖蜂窝的「什么时候该到下一站」信息来源——站间时长由真实通勤数据免费产生（与 10-09 变更记录既定方向一致）。

## 三、机制设计（v0.1 草案）

### 3.1 触发规则（核心）

```
锚点 = 最近一次计数（STATION_ARRIVED 的 lastCountedMs + stationCount）
触发 = now - lastCountedMs >= cumulative(stationCount+1 .. k-1 各段 min) - leadSec
      且 !arrived 且 !alertDestSoonSent
动作 = 发 ALERT_DEST_SOON（现有「即将到达 X，请准备下车」，复用文案/通知 ID/去重位）
```

- `cumulative` = 从当前已计数站到目的站前各段 min 之和（站区漏检多站时按已计数站折算，自适应）。
- `leadSec` 默认 **40 s**（TuningConfig `timeFallbackLeadSec`），可调。
- 与站区通道共用 `alertDestSoonSent` 去重位——**谁先到谁发**，天然不重复。
- 纠错 `±1` 已更新 `lastCountedMs`（现有机制），时间兜底自动跟随，无需额外处理。
- 起点保护：`stationCount ≥ 1` 才启用（预热/上车站段不发）；`k=1` 特例沿用现有预热即 D−1 逻辑（本兜底不发）。

### 3.2 落点与资产

- **core（纯 Kotlin）**：`MonitorSession` 增 `timeFallback` 分支；新增输入 = 每方向每段 `minSeconds` 数组（构造参数，缺省 null = 关闭）。
- **资产**：新增 `assets/segment_times.json`（或并入 `cell_zones.json` 升 schema——二选一，倾向独立文件，职责清晰）：
  ```json
  {"lines": [{"lineId":"cd6","directionId":"cd6_to_lanjiagou","segments":[
      {"from":"cd6_s27","to":"cd6_s28","minSec":126,"medSec":134,"samples":3}, ...]}]}
  ```
  生成：扩 `gen_cell_zones.py`（或独立脚本）从学习趟 lab MARK 离线产出；**无隐私（只有时长与公开站序）**。
- **TuningConfig**：`timeFallbackEnabled`（默认 false，验证后开）、`timeFallbackLeadSec=40.0`。
- **platform**：`MonitorService` 加载资产传入会话（同 `CellZoneMap` 路径）。

### 3.3 与现有机制关系

| 机制 | 关系 |
|---|---|
| 站区 DEST_SOON（进目的站区触发） | 共享去重位；单元数据时站区版先发（进区早于到站 0~58 s），蜂窝哑时时间版顶上 |
| 50 s 目的站兜底（进区后兜底计数） | 不动（计数域）；时间版只管「发提醒」，不产计数 |
| D−1（进 D−1 站区） | 不动（仍是站区触发）；时间版 v0.1 不覆盖 D−1（如需，同法以 `cumulative(..k-2)` 加一级，评估后追加） |
| v3/v4 计数 | 不动；时间版只读 `stationCount/lastCountedMs`，**不改变计数与结束判定** |

### 3.4 风险与边界

- **先验方差**：个别段 30~80 s（早 6 临停）→ 取 min + lead 40 s，最坏提前 ~2 min 发「即将到达」（符合用户「早发无害」口径；如太早再调 lead）。mapped 数据只有 3 趟 → 随通勤趟数自动滚动更新（gen 脚本重跑）。
- **计数全漏时**：锚点消失（`stationCount` 不前进）→ 时间版也不会发。属已知边界（计数由 IMU 通道兜底，两通道同时失效=无解）；后续可评估「多站累计 + 软进度」增强，不在 v0.1。
- **换乘/支线扩展**：每方向独立先验，天然隔离。
- **合规**：纯 core + 资产 + TuningConfig；无新权限；无坐标。

## 四、验收（待实施）

1. **合成用例**（0 蜂窝样本 + 时间兜底开）：到站前 ~40 s 发「即将到达」且仅一次；`stationCount=0` 不发；已 `arrived` 不发。
2. **replay**：10-10 晚 6 号线数据 + **剥掉全部有值拍**（纯空流）→ 「即将到达」仍在目的站前发出（证明不依赖蜂窝）。
3. **现场**：下一趟通勤 App 后台跑，检查「即将到达」是否在开门前到达（对照 MARK）；同时观察是否与站区版重复（应无）。
