## 一、总评

**四份文档构成完整证据链（选型 → 架构 → 设想 → 数据），质量很高；核心论断逐条验证后基本全部属实。**

- **第一批的 P0-1（定位权限耦合）是真雷**——评审点透之前，本项目文档体系（含
  `CellMonitorCollector` 的 KDoc）都未识别的隐式依赖；
- **第二批的「发现 1（gNB 键）」是真金**——跨天泛化命中率 82% → 93%，把 09-30 晚通勤
  「扇区漂移」三例中的两例（陆肖、三官堂）结构化为**同 gNB 异扇区**，一次键折算即可救回，
  不必等多趟合并；「发现 2（`Int.MAX_VALUE` 缺陷）」是代码 + 数据双确认的真缺陷（可立即修）；
- 与项目既有结论（不定位、不用坐标、无网络依赖）的相容性均无问题；
- P0-1 升格 `ACCESS_FINE_LOCATION` 与「不定位」裁决不冲突——权限是平台对 CellInfo 的
  校验门槛，不是能力使用声明；引用自检恰好把「只读标识、不读坐标」变成可回归约束。

## 二、第一批复核：调研报告 + 架构评审

### 2.1 P0-1 定位权限耦合 —— ✅ 属实（附 3 个评审未点透的加重因素）

| 证据 | 位置 | 内容 |
|---|---|---|
| Manifest 注释 | `AndroidManifest.xml:4-8` | FINE / COARSE 注释明确写「主功能不申请不读取；采集需求下线时一并移除」——按注释执行即打穿 v4 |
| 主链路 KDoc | `CellMonitorCollector.kt:21` | 只声称「权限：READ_PHONE_STATE」——注释本身漏了 FINE_LOCATION（Android 10+ 读 CellInfo 必须 FINE，否则 `getAllCellInfo()` 空、`LISTEN_CELL_INFO` 无回调） |
| 坐标 API 引用 | 全仓 grep | `android.location.*` 仅在 `platform/lab/LabCollectorService.kt`（loc 流）——引用自检与现状吻合，固化成测试零成本 |

**补充的加重因素**：

1. **失效是静默的**：`CellMonitorCollector.kt:46` 的 `runCatching { tm.listen(...) }`
   在无位置权限时照样成功并返回 `true` → 不触发 v3 降级。**现在**用户在系统设置撤销位置权限
   即可复现。修复时应加「首拍为空 / 持续无样本 → 可见反馈或降级」的活性检测；
2. **运行时授权也是缺口**：当前运行时授权挂在 lab 启动链路上，lab 下线后主链路需要自己的
   权限请求路径 / 无权限可见反馈（与硬性规则 5 的 FGS 反馈同理）；
3. **P0-2 方案同样压在这条权限上**：Android 12（API 31）起 `requestCellInfoUpdate`
   要求 `ACCESS_FINE_LOCATION`（官方兼容性变更）——P0-1 与 P0-2 必须一起定。

### 2.2 P0-2 小区流拍点稀疏 —— ✅ 根因属实，一处 API level 修正

无主动拉取驱动、回调节奏由系统缓存刷新决定，与「146 处断档 / 比高德慢」因果链成立。
**修正：`requestCellInfoUpdate(Executor, CellInfoCallback)` 是 API 29（Q）引入**，评审写
「API 30+」不准（API 30 加的是 WorkSource 重载）。minSdk 26 的守卫写 `>= Build.VERSION_CODES.Q`。

### 2.3 P0-3 shouldWrite 签名失真 —— ✅ 属实，严重性下修

`LabCellCollector.kt:111` 的 `cellsSignature = formatCells`（含 rssi）与注释「切换不落节流窗」
语义不符。**但「写入密度失控」实测未发生**——当晚主链路 cell 流约 30 s/行（回调稀疏是主节奏），
2.8 s / 17.8 s 的短行恰是 rssi 变化触发的「变化即写」痕迹。结论：**语义修复，不是救火**，
归节后装机批次。

### 2.4 P1-1 序列级概率解码（HMM/Viterbi） —— ✅ 方向认可，先离线原型再立项

「硬匹配对漂移零容忍」被晚通勤 3 例纠错充分证明；4 个遗留问题一次消解的论证成立。
但落地必动 `core/cell/`（红线内），且发射概率标定、参数全进 `TuningConfig`（硬性规则 2）
都是工程量。建议节中先在仓库外做离线原型（今晚/今早 CSV），拿数据再立项。
**与批次 C 的 gNB 键折算的关系见 §5 批次 C 注**。

### 2.5 P1-2 TA 采集 —— ✅ 同意「立刻采」，附两条预期管理

- **兼容性好消息**：消费端都是 `split(":")[:2]` 取前两段，行格式扩成 `pci:ci:rssi:ta`
  不破坏既有解析；
- **预期管理 1**：TA 在漏缆 DAS（多 RRU 同小区）下单调递增**不是理论必然**——701 这类
  小区的 TA 行为恰恰是要用它解决的问题本身，只能采回来实测；
- **预期管理 2**：K80 / HyperOS / Android 17 上 `getTimingAdvance()` 可能恒返回
  `Integer.MAX_VALUE`——先看第一行数据再谈 78 m/格标定。

### 2.6 P2 / P3 —— ✅ 属实

- displayState 抽纯函数方向对；接线动 `MonitorSession`（红线内），纯函数 + 单测可先写、
  接线等节后；
- 气压计（CN111222836A）归档总纲「后续优化」，换机后启用；

## 三、第二批复核：设想评审 + 多趟通勤数据分析

### 3.1 gNB 键跨天泛化实验（发现 1/3）—— ✅ 关键数字独立复算全部吻合

对 09-30 晚「漂移三例」+ 顺江路逐个做 `NCI = gNB << 12 | cellId` 分解：

| 站 | 映射键 | 次日实测 | gNB 关系 | 与文档一致？ |
|---|---|---|---|---|
| 陆肖 | gNB 9437641 / cellId 42 | gNB 9437641 / cellId 2 | **同 gNB 异扇区** | ✅（救回名单内） |
| 三官堂 | gNB 9444004 / cellId 43 | gNB 9444004 / cellId 41 | **同 gNB 异扇区** | ✅（救回名单内） |
| 顺江路 | gNB 9443995 / cellId 41 | gNB 9443995 / cellId 2 | **同 gNB 异扇区** | ✅（救回名单内） |
| 琉璃场 | gNB 9444006 | gNB 9443998 | **不同 gNB** | ✅（不在救回名单，精确自洽） |
| 市二医院 | 701 → gNB 9438163 | 820 → gNB 9438162 | **不同 gNB**（编号相邻） | ✅（不在救回名单） |

结论：文档「gNB 键救 2/3」**没有夸大**；琉璃场（跨方向站台共用室分小区——已验证 879 的
NCI 在望丛祠方向映射表中合法存在）与市二医院仍需多趟合并 / TA / 重学。
**「pci 会漂移、ci 稳定」「pci 不该进主键」的推论成立**——现状 `pci:ci` 等于给映射表绑了
一个会变的前缀，gNB 折算（`CellZoneMap` 加载时 `ci >> 12`，**不动资产文件**）可同时
吸收同站扇区并摆脱 pci 前缀。

### 3.2 `ciOrUnknown` 漏滤 `Int.MAX_VALUE`（发现 2）—— ✅ 代码 + 数据双确认，可立即修

- 代码：`LabCellCollector.kt:153` 只滤 `Long.MAX_VALUE`，而 LTE/WCDMA/GSM/CDMA 的
  ci 未知哨兵是 `Int.MAX_VALUE`（`.toLong()` 后 ≠ `Long.MAX_VALUE`）→ 伪小区落盘；
- 数据：今晚 `cell_20260930_172924.csv:87`（t=444121178）确有 `184:2147483647`
  （当晚报读该行时未识别，被外部分析抓出）；
- **已 grep 确认现 `cell_zones.json` 无伪小区** → 当前是防御性修复，未造成实际伤害；
- 修复一行 + 回归用例；`platform/lab/` 不在判定路径冻结清单内（其纯函数被主链路复用，
  改动走 126 项测试门）。gen 脚本同步加「拒绝 ci = 2147483647 / −1 进表」断言。

### 3.3 rssi 判停动否定（设想评审②）—— ✅ 论证认可，节中挖掘目标随之更正

- 快衰落速率 v/(λ/2) ≈ 289 个/秒（2.6 GHz、60 km/h）数学正确；0.2 Hz 采样 +
  停稳期自身摆幅 13 dB ≫ 站间判决差 4 dB——**采样率与噪声两个层面都堵死**；
- 与需求第十节单趟初挖（中位差 4 dB）互证，且多趟复核（发现 8）维持「不可分」；
- **对节中工作的影响**：rssi 挖掘目标从「判停动（❌ 出局）」更正为
  **「站内（室分）vs 隧道（漏缆）分布特征」+ 701 拆分（次优先，让位 TA）+ TA 同批采集**；
- 「IMU 的优势 = 快 238 倍的时间分辨率使时序结构可建」的更正表述准确（旧「方波 20 倍对比度」
  口径撤回正确——09-25 资产量纲已变）。

### 3.4 服务端闭环（设想评审④）—— ✅ 四处更正全部认可，暂缓建服务器

「隧道里有蜂窝网——没有网就没有小区数据，v4 整条主通道都不成立」——触发条件应为
**网络可用（优选 Wi-Fi / 充电）**而非 GNSS 恢复，这条最关键；「AI 分析 = 序列对齐」、
「下发需运行时可写存储 + 版本 + 回滚 + 合并」、「纠错回传缺失否则单向通道」均成立。
**结论「假设验完之前不建服务器」与项目无网络依赖原则一致**；若将来动手，先只做纠错回传。

### 3.5 双卡交叉学习（设想评审①）—— ✅ 方向对、入口对

键空间先升 `mcc:mnc:pci:ci` + 卡槽字段，再做异网交叉——排序正确。本项目双卡为移动（槽 0）
+ 联通（槽 1）**异网成立**（收益前提满足）；副卡是否常驻 2G（GSM 无 PCI）需实测确认。

### 3.6 三处小瑕疵（建议原作者或后续会话顺手修）

1. **文档间更正未回写**：多趟分析发现 7 将设想评审§三「邻区兜底是死代码」修正为
   「偶发触发（0.3%~3.6%）」，但设想评审原文无更正注——先读者会被误导；
2. 设想评审 P1-b 称 TA「单调稳定」，比架构评审「需实测标定」口径强——统一为
   「待实测验证」（漏缆 DAS 下单调性非理论必然）；
3. 发现 1 实验表中 `20260930_172016` 为方向选反会话，50% 命中的解读有对齐歧义
   （发现 6 已注 ※，发现 1 表未注；影响极小）。
