## 一、结论速览

**Cell ID 方案可行，但单独使用不成立。** 准确的说法是：它是必要的"锚点信号"，但不是充分的"到站判据"。

| 判断维度 | 结论 |
|---|---|
| 技术上能否定位到"某一站" | **能**。站厅/站台采用室内分布系统，小区划分精细（几十米至一两百米），可把用户限定在站点级范围内 |
| 技术上能否定位到"隧道中的位置" | **基本不能**。隧道漏缆覆盖下，一段数公里可能只配置 1 个小区，Cell ID 在数百米到数公里内完全不变 |
| 能否判定"列车停稳、开门" | **不能**。这是 Cell ID 方案的死穴 —— 小区边界与站台不对齐，且工程上站台常与隧道划为同一小区 |
| 是否有纯 Cell ID 的商用产品 | **没有**。所有可用的产品（高德、百度等）都是 Cell ID + 传感器 + 指纹库的融合方案 |
| 最大的非技术风险 | **iOS 完全不可用**。苹果不向第三方开放任何基站/Wi-Fi 列表数据 |
| 推荐做法 | Cell ID 作为锚点 + IMU 里程推算 + 气压计开门特征 + 线路拓扑/时刻表先验，用状态机把"进站""停稳""到站确认"三个事件严格分离 |

一句话概括能力边界：**Cell ID 能告诉你"我进入了 X 站的覆盖区"，不能告诉你"列车已经停稳开门"。**

## 二、你已验证失败的两条路线，问题出在哪

这不是你的实现问题，是物理与工程层面的必然结果，且已有专利文献明确记录：

1. **卫星定位（GNSS/GPS/北斗）**
   地铁隧道为地下封闭空间，卫星信号被地层完全屏蔽。这是物理规律，无工程手段可绕过。

2. **纯传感器 / 行为识别**
   专利 **CN111222836A**《一种到站提醒方法及相关装置》在背景技术中直接给出了否定结论：
   > "第二类第三方应用在 Cell ID 定位技术上增加加速度判断技术……但由于加速度传感器数据受手机状态影响较大，用户主动或被动移动手机，都会造成数据干扰，导致无法准确判定列车运行状态。例如，用户移动手机和列车变轨抖动。"

   这正是你"人在车厢与平地难以区分"的实测结论的文献印证 —— 干扰源来自**用户自身动作**与**列车变轨抖动**，而非算法不够好。

同一份专利还给出了 Cell ID 单独使用的否定结论：
> "由于 Cell ID 定位精度很差，无法准确获知列车运行状态，即列车在运行中、停靠开门还是停靠关门。Cell ID 定位精度在市区一般可以到达 300-500m，郊区甚至可以到达几公里，定位精度通常大于一个站点的长度。"

**这两段话同时否定了你走的两条路 —— 以及你要评估的这第三条路。** 但它也指明了出路：该专利最终采用的方案是"气压传感器开门特征 + 定位区域"双重判定。这个方向后面会详细展开。

## 三、Cell ID 定位原理

### 3.1 标识体系

移动终端接入一个小区时，网络为其分配一个小区的全球唯一标识：

```
CGI (Cell Global Identity) = MCC + MNC + LAC/TAC + CI
                             │      │      │        └─ Cell Identity 小区号
                             │      │      └─ Location/TA Code 位置区
                             │      └─ Mobile Network Code 网络码（运营商）
                             └─ Mobile Country Code 国家码（中国 = 460）
```

在 4G/5G 中，终端侧还会拿到 **PCI（物理小区标识）** 以及邻区的 **RSRP / RSRQ / SINR** 等无线测量值。

### 3.2 三种实现路径，能力差异极大

| 路径 | 原理 | 第三方 App 能否使用 |
|---|---|---|
| **纯终端的服务小区读取** | 直接读当前注册小区的 CGI | ✅ 能（Android），但精度最差 |
| **终端 + 邻区指纹匹配** | 服务小区 + 邻区集合 + 各邻区 RSRP 构成"指纹"，与预先采集的指纹库匹配 | ✅ 能，这是唯一有实用价值的路径 |
| **网络侧定位（CID / E-CID）** | 由网络侧 GMLC / SMLC / LMF 参与，结合 TA（时间提前量）、RSRP、AoA 做多边定位 | ❌ 不能，需运营商网络权限（注：**TA 本身的终端侧可读性见上方「归档说明」修正项**） |

**这里有一个容易踩的坑**：3GPP 标准中真正叫 "Cell-ID Positioning Method" 的是**网络侧方法**（3GPP Release 5 引入，服务于 E911/E112 紧急呼叫定位），它需要 GMLC → SMLC/MME → 基站的完整信令链路。第三方 App 拿到的只是终端自己能读到的 CellInfo 快照，**两者不是一回事**。E-CID（LTE R9 起）通过叠加 TA 和 RSRP 把精度提升到中等水平，同样需要网络侧参与。

### 3.3 Android 侧的可用性与限制（关键工程约束）

| 项目 | 说明 |
|---|---|
| 主 API | `TelephonyManager.getAllCellInfo()` / `getCellLocation()`、`TelephonyCallback.CellInfoListener` |
| 返回内容 | 服务小区 + 邻区，含 CellIdentity、信号强度、`getTimestamp()`；`isRegistered()` 标识是否为当前服务小区 |
| 权限门槛 | **Android 9 及以下**：`ACCESS_COARSE_LOCATION` 即可；**Android 10+**：必须 `ACCESS_FINE_LOCATION`。注意——要求精确定位权限 ≠ 必须开启 GPS，用户只需开启"位置服务"并允许网络定位即可 |
| 刷新机制 | **Android Q 起，调用 `getAllCellInfo()` 不再触发主动刷新**，只返回缓存结果。需改用 `requestCellInfoUpdate()`，且官方明确"updates will be rate-limited and are not guaranteed"（限流且不保证） |
| 数据新鲜度 | 必须用 `CellInfo.getTimestamp()` 判断数据陈旧程度，不能假定实时 |
| 后台限制 | 后台进程（含 Android 11+ 的 Foreground Service 场景）会被系统短路返回 null |
| OEM 限制 | 部分厂商（EMUI/MIUI/ColorOS 等）在 Android 11+ 默认对非系统签名应用屏蔽该接口 |
| **iOS** | **完全拿不到**。高德官方技术文章明确写道："在 iOS 上由于苹果公司未开放任何定位相关的指纹数据（Wifi、基站列表等），定位结果全部来自于 iOS 自身。" |

**iOS 这一条是决定性的。** 如果你的目标用户包含 iPhone，整个方案在 iOS 上无法按此路径实现，只能退回"传感器 + 时刻表"路线。

### 3.4 为什么"地铁"是 Cell ID 最糟糕也是最合适的场景

这是整份报告最核心的工程事实 —— 地铁的无线网络**同时具备两种极端形态**：

**（A）车站内（站厅 / 站台）—— 定位能力最好的地方**

地铁站采用室内分布系统（DAS）、小基站或分布式射频单元（pRRU）覆盖，并按站厅、站台、换乘区域等功能区划分多个小区。每个小区覆盖范围较小，通常仅覆盖**几十米至一两百米**。小区划分精细、覆盖边界明确，是站点级定位的良好数据源。

**（B）隧道区间 —— 定位能力最差的地方**

站间区间普遍采用**泄漏同轴电缆（漏缆）**实现连续覆盖。漏缆按约 **500 米**断开布放设备，但**一段数公里长的隧道可能仅配置一个或少量无线小区**。终端在很长距离内始终连接同一个 Cell ID 和 PCI。

引用一线工程分析的原文举例：
> "例如，列车距离 A 站 100 米、800 米甚至 2000 米时，终端可能始终连接同一个小区，从 Cell ID 角度无法判断列车具体位于隧道哪个位置。"

**（C）最致命的一条工程惯例**

地铁网络的分区原则中有一条标准做法：
> **"站台和站厅不同小区覆盖，保证容量；站台和隧道覆盖同小区，避免大量切换集中出现。"**

也就是说 —— **列车停靠站台时，Cell ID 很可能根本不发生变化**，因为站台和隧道本来就是同一个小区。切换发生在**隧道中段**，而不是站台。

这意味着：即使你完美实现了 Cell ID 变化检测，得到的也是"列车正在隧道中某处"，而**恰好不是"列车已到达站台"**。

> 注：不同城市、不同线路、不同运营商的做法并不统一。部分线路站台确实独立成小区（这时进站会触发切换，是有用的锚点）。**这意味着方案的可行性在成都地铁的不同线路上可能是不同的**，必须在目标线路上实测确认。（**实测结论见上方「归档说明」：站区驻留识别成立，12/12 覆盖。**）

## 四、风险分级

| 级别 | 问题 | 后果 | 处置建议 |
|---|---|---|---|
| **P0** | iOS 不开放基站/Wi-Fi 列表 | iOS 端方案完全不可实现 | 明确 Android only；iOS 走传感器 + 时刻表退路 |
| **P0** | 站台与隧道同小区 → 停靠无切换 | 无法判"到站"，方案在主流程失效 | 目标线路逐站实测小区边界，确认可用的切换锚点 |
| **P0** | 隧道内单小区跨数公里 | 站间位置完全不可分辨 | 不依赖 Cell ID 做站间推算，改用 IMU 里程推算 |
| **P0** | Android 10+/14 权限与限流；后台返回 null | 无法持续采样，数据陈旧 | 前台服务 + `requestCellInfoUpdate()` + 时间戳校验；预留降级路径 |
| **P1** | 无官方基站位置数据库 | 需要自建指纹库，冷启动成本高 | 众包采集（见 CN103179511B、高德的双策略） |
| **P1** | 双卡 / 多运营商 | 同位置不同运营商 Cell ID 完全不同，指纹库需按运营商分别建立 | 指纹库按 MMN 分片；或仅用服务小区序列做相对判断 |
| **P1** | 列车甩站（越站运行）、区间临时停车 | 站序推断错位，误报 | 不与绝对站序强绑定，用"车站特征指纹"匹配而非"第 N 站" |
| **P1** | 手机飞行模式 / 关机 / 弱覆盖掉网 | 信号链断裂 | 检测到长时间无 CellInfo 时自动切降级模式 |
| **P2** | 换乘站多线路小区混杂 | 线路归属误判 | 结合线路拓扑与进入方向做约束 |
| **P2** | 新建线路 / 网络改造后小区规划变更 | 指纹库失效 | 指纹库需要版本化与定期重采 |

|---|---|---|
| **高德地图** | 官方技术博客《高德网络定位算法的演进》 | 原文直言地铁场景："**用户扫到的 Wifi 基本都是移动 Wifi**（少量车站有固定 Wifi），因此**只能借助基站进行定位**。但基站深埋地下，缺乏采集数据。" 解法：① 利用相邻基站（同时扫到"地铁基站"与"非地铁基站"时用后者位置推算前者）② **利用用户轨迹精准挖掘出每个请求对应的地铁站**，构建指纹真值。结论："**地铁内的定位精度可达到 90% 以上，实现地铁报站和换乘提醒**"。⚠️ 仅 Android |
| **百度地图** | 2022 年"精准地铁定位技术"，北京首发，Android 先行 | 学习地铁内 **Wi-Fi、基站等有源信号的变化规律**，结合地铁线路拓扑与站点规划布局，构建**深度学习模型**做站点识别；同时用机器学习构建**地铁状态预测模型**（驶出/行中/进站/停车），**明确提到"排除地铁车厢内乘客行走、晃动等行为干扰"** |
| **Google Now / Google Maps** | 位置 + 网络信号 + 时刻表 | 在有信号时按实际位置计算，地下覆盖受限时**退回时刻表与预计时长** |
| **首尔交通公社「또타지하철」到站提示铃** | **超声波** | 列车到站时由地铁用**人耳听不到的超声波**把到站内容推给 App。这是绕开所有网络定位问题的另一种思路 —— 但需要运营方配合 |
| **「别睡过站 GPS 到站提醒」等纯 GPS App** | 纯 GPS 距离围栏 | 官方 FAQ 自己承认："**隧道中 GPS 信号可能减弱**。当列车出隧道后，应用会重新定位并触发提醒" —— 即纯 GPS 方案在地下根本不工作 |

### 5.4 关键判断

**没有任何一个主流可用产品是"纯 Cell ID"。** 凡是能用的，都做了融合：

- 高德 = 基站指纹 + 众包轨迹真值 + 相邻基站推算
- 百度 = Wi-Fi/基站有源信号 + 深度学习 + 传感器状态机
- SubTrack（学术）= Cell ID 进站检测 + IMU 跟踪
- CN111222836A（专利）= 气压计开门特征 + 定位区域

你的方案要成立，路径也是同一条。

### 6.1 几个值得单独说明的方案

**超声波 / 声学方案（首尔地铁已落地）**
这是唯一一个"绕开定位问题"的思路 —— 不定位，而是由**运营方直接广播到站信息**。首尔交通公社已在 2/3/4 号线试运行，计划扩展至 1–8 号线。优点是精度高、零基础设施争议；缺点是需要地铁公司配合，且 App 需要有麦克风常驻权限。

**气压计方案（专利 CN111222836A 的落点）**
气压计对**车厢内因开关门引起的气压扰动**有独特敏感性。该专利把每次开门/关门的气压数据用滑动窗口转成 3TF 维特征向量（含气压值 PV、方差 V、拟合斜率 k），再用聚类得到"开门中心特征向量 + 聚类半径"，通过距离判定是否为开门事件。这是**目前最直接解决"停稳开门"判定问题**的公开技术方案，强烈建议纳入你的方案。（**注：本机 K80 无气压计，见上方「归档说明」。**）

**IMU 里程推算（SubTrack 的做法）**
用加速度二次积分得到速度与位移，再沿线路里程轴累加。关键是必须有锚点定期重锚（否则漂移）。Cell ID 恰好可以充当这个锚点 —— 这就是两者结合的逻辑闭环。

## 七、推荐方案与落地路线

### 7.1 架构（四层）

```
感知层    CellInfo（服务小区 + 邻区 RSRP） / IMU / 气压计 / 线路拓扑与时刻表
              ↓
融合层    无线指纹匹配 + 里程推算 + 时间先验 → 滤波融合
              ↓
判定层    进站事件（切换点/指纹命中） · 停稳事件（IMU 静止 + 气压突变） · 到站确认（两事件与站序一致）
              ↓
输出层    语音播报 / 振动 / 通知   ← 兜底：Cell ID 长时间不变时退化为时刻表 + 里程推算
```

### 7.2 三个事件必须严格分离

这是整个方案成败的关键。把"到站"拆成三个独立判据，任一单独失效都不会导致误报：

| 事件 | 判据 | 触发源 |
|---|---|---|
| **进站** | 服务小区发生切换，或邻区指纹命中某站特征 | Cell ID / 指纹库 |
| **停稳** | IMU 合加速度方差趋近 0 且持续 > 2 s | 加速度计 |
| **开门** | 气压特征向量落在"开门中心特征向量"的聚类半径内 | 气压计 |
| **确认提醒** | 进站 ∧ 停稳 ∧（开门 ∨ 超时）∧ 与站序一致 | 逻辑与 |

**只依赖其中任一单项都是不可靠的** —— 这正是 CN111222836A 与百度方案共同的做法。

### 7.3 指纹库的冷启动（这是最大的工程成本）

无人踏勘的情况下，可参考高德与 CN103179511B 的双策略：

1. **众包采集**：App 在站台停稳时（由 IMU 判定）自动上报当前 CellInfo 快照 + 由用户确认的站名，逐步积累指纹
2. **相邻基站推算**：当设备同时能看到"地铁小区"和"地面小区"（进站/出站瞬间）时，用地面小区的已知位置反推地铁小区位置
3. **轨迹挖掘**：利用用户轨迹序列反推每个 CellInfo 快照对应的地铁站（高德的做法，精度最高但实现最重）

### 7.4 建议的推进顺序

| 阶段 | 目标 | 交付 |
|---|---|---|
| **第 0 步（必须先做）** | **在目标线路实测小区边界** | 结论：站台是否独立成小区？切换点距站台多远？成都地铁不同线路是否一致？ —— **✅ 已完成，见「归档说明」** |
| 第 1 步（MVP） | Android only，Cell ID 切换 + IMU 静止 + 气压开门三判据 | 可用的到站提醒 |
| 第 2 步 | 引入众包指纹库，提升进站判定的鲁棒性 | 覆盖更多线路 |
| 第 3 步 | 加入时刻表先验与到站时间预测 | 提前一站提醒 |
| 第 4 步 | iOS 分支：传感器 + 时刻表退路 | 全平台覆盖 |

**第 0 步是最关键的一步。** 整份报告的结论建立在"地铁工程惯例"的公开描述上，但不同城市、不同线路、不同运营商的实际做法差异很大。**花一天时间在成都地铁 1~2 条线路上做一次 CellInfo 采样，就能把这份报告里所有"可能"变成"确定"。**（**该步骤已完成。**）

### 7.5 与现有资料结合

成都地铁已开通运营 **489 个车站**、运营里程 **758 公里**（漏缆超 2000 公里）。按此折算，**平均站间距约 1.55 公里**。

这个数字有直接意义：它意味着站内精细小区（几十至两百米）的定位粒度**远小于**站间距，站点级区分是可行的；但隧道段的 Cell ID 粒度（数百米至数公里）**接近甚至超过**站间距，站间区分是不可行的。仓库内 `app/src/main/assets/subway_lines.json`（成都 4/6 号线全量站点，WGS-84，来源见 `spec/done/real-line-data/`）已包含站点坐标，可直接用于计算各线路的实际站间距分布，作为"哪些区间必须靠 IMU 推算"的量化依据。

## 九、最终判断

| 问题 | 回答 |
|---|---|
| Cell ID 方案是否可行？ | **可行，但必须作为融合方案的一部分，不能单独使用。** 它能可靠解决"进站锚点"，不能解决"停稳开门判定"，而后者恰恰是到站提醒的核心 |
| 最大的技术死穴是什么？ | **地铁工程的"站台与隧道同小区"分区原则** —— 这会让列车停靠站台时不产生任何 Cell ID 变化。这是必须在目标线路实测验证的第一件事 |
| 最大的非技术死穴是什么？ | **iOS 不开放基站列表**，方案天然只能覆盖 Android |
| 已有类似实现吗？ | **有，且很多** —— 5 项相关专利、4 篇核心论文、高德/百度/首尔地铁/Google 四个商业落地案例。但**没有一个是纯 Cell ID** |
| 应该怎么做？ | 按第七节四层架构：Cell ID 锚点 + IMU 里程推算 + 气压计开门特征 + 时刻表先验，三事件分离判定 |
