# 行程历史数据库与历史列表

> 归属里程碑 S4（M3）「打磨」（总纲第九节）；写入侧可提前与 [`../csv-storage-policy/需求.md`](../csv-storage-policy/需求.md) 一起落。

## 一、要解决的问题

现在唯一的持久记录是 CSV 三件套：它**面向回放调参**（50 Hz 原始数据），不是面向「用户回看」，而且体积大、会被清理策略删除。于是：

- 无法回答「上周三那次通勤为什么提前提醒」「我这条线一共坐了多少次、识别准不准」；
- CSV 被清理后，行程信息**彻底消失**；
- 总纲第十一节 #6「历史行程统计」缺一个基础数据层。

## 二、目标

1. 每次行程结束写入**一条行程摘要**（几百字节）+ N 条停站明细；
2. **与 CSV 解耦**：`meta.json` 里的信息冗余进库，CSV 被删后摘要仍完整可读；
3. 最简 UI：设置页「历史行程」列表（最近 50 条，支持删除单条 / 清空）；
4. **零新增第三方 / 注解处理器**：用平台 `android.database.sqlite.SQLiteOpenHelper`。**不引入 Room** —— 单表 + 个人自用，Room 会引入 KSP 与版本匹配风险（与 `docs/development.md` 的「稳妥版本组合」原则冲突）；
5. 写库不阻塞主线程、不阻塞服务停止。

## 三、数据模型（草案 v1）

### 表 `trip`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `started_at_ms` / `ended_at_ms` | INTEGER | UTC 毫秒 |
| `line_id` / `line_name` | TEXT | |
| `direction_id` | TEXT | |
| `boarding_id` / `boarding_name` | TEXT | |
| `destination_id` / `destination_name` | TEXT | |
| `k` | INTEGER | 计划停站数（`RouteSpec.k`） |
| `detected_stops` | INTEGER | 识别并计数的站数 `n` |
| `corrections` | INTEGER | 手动 ±1 纠错（净值） |
| `end_reason` | TEXT | `manual` / `arrived` / `timeout` / `error` |
| `alerts_sent` | TEXT | 实际发出的提醒（逗号分隔，如 `PREV,ARRIVED`） |
| `data_gaps` | INTEGER | `DATA_GAP` 次数 |
| `csv_stamp` | TEXT NULL | 关联的 CSV 会话名（CSV 被清理后仍保留该值） |

### 表 `trip_stop`

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | |
| `trip_id` | INTEGER → `trip(id)` ON DELETE CASCADE | |
| `seq` | INTEGER | 从 1 起 |
| `station_id` / `station_name` | TEXT NULL | 当时按 `n` 推算的站名（纠错后可能不等于实际） |
| `arrived_at_ms` | INTEGER | 到站时刻（UTC） |
| `dwell_s` / `interval_s` | REAL NULL | 停站时长 / 与上一站间隔（由 `DEPART` 事件回填） |
| `counted` | INTEGER | 是否计入 `n`（首站忽略 / `STOP_SUSPECT` 记 0） |
| `note` | TEXT NULL | 状态机 note（`vib=` / `still_no_brake` / `boarding_station` …） |

索引：`trip(started_at_ms DESC)`、`trip_stop(trip_id, seq)`；`PRAGMA user_version` 管版本。

### 写入时机

`MonitorService.teardown` 里**单事务**写完（`beginTransaction` / `setTransactionSuccessful`），放 IO 线程。**不逐样本写库**（50 Hz 写库没有意义且伤性能）；异常结束（被杀 / 崩溃）不产生半条数据（要么整条要么不写）。

## 四、待决策（开工前确认，确认后 `status: planned → ready`）

| # | 问题 | 建议 |
|---|---|---|
| 1 | 列表展示哪些字段 | 时间、线路、上车站 → 目的站、识别 / 计划站数、是否纠错、耗时 |
| 2 | 是否需要「删除单条 / 清空」 | 都要（个人数据，可控） |
| 3 | 行程摘要是否也设保留上限 | 不设（条目极小，手动清空足够） |
| 4 | 是否记录提醒延迟用于统计 | 记录：`alert_prev_at_ms` / `alert_arrived_at_ms` 两列，可算「D−1 提醒比到站早多久」 |
| 5 | 是否顺带做统计（次数 / 准确率图表） | 本期不做，仅列表；统计另立需求 |

## 五、验收标准（草案）

1. 一次完整行程 → `trip` 1 条 + `trip_stop` N 条（**含被忽略的首站，`counted = 0`**）；
2. 手动 / 到站 / 超时三种 `end_reason` 均正确落库；异常结束不产生脏数据；
3. 删掉 CSV 目录全部文件后，历史列表内容**不变**；
4. `user_version` 1 → 2 迁移用例（新增字段）不丢数据；
5. 真机：20 条停站的写库耗时 < 50 ms；服务停止不被写库阻塞；
6. `gradlew test` 全绿（覆盖纯逻辑部分，见风险表）。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| `android.database` 不能用于 JVM 单测 | 「事件流 + UiState → `TripRecord`」的组装放 `core`（纯 Kotlin，可测）；DAO 层保持极薄（只做 Cursor ↔ `TripRecord` 映射），真实 DB 读写靠真机自测 |
| 迁移写错导致数据丢失 | v1 只建表；迁移函数 + SQL 拼接单测 |
| 隐私 | 仅存本机 App 私有目录，App 无任何网络权限，天然不上传 |
