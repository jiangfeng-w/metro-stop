# UI 滑动与下拉框掉帧诊断与修复

## 一、症状（2026-09-27 用户实测反馈）

1. **页面上下滑动掉帧**：无论**是否在监测**都会出现；相对症状 2 较轻微。
2. **下拉框互切掉帧**：展开一个下拉框后，**点开另一个下拉框**时明显掉帧（"卡卡的"），比滑动严重；已确认只能发生在**未监测**时（监测中下拉框整体禁用，见 `RouteSelector.enabled = !state.running`）。

## 二、目标与验收口径

- 用设备数据（`dumpsys gfxinfo` framestats / 必要时 Perfetto）**先取证**，定位到可量化的环节；✅ 已完成（见诊断报告 §5）
- 修复后对照：同等动作序列（同口径脚本复跑 C1/C2/A1/B1）下 Janky% 明显下降、无连续多帧掉帧，**主观上滑动与互切不再"卡卡的"**；
- 全程遵守通勤实测红线（第五节）。

## 三、范围

- **包含**：UI 重组范围与上报频率（`MonitorService` 的 UI 上报侧）、`AppScreen` / `RouteSelector` 等 UI 层结构、Compose 交互路径。
- **不包含**：算法路径（`core/fsm/`、`core/feature/`、`TuningConfig`、`SensorCollector`、监测循环）——红线冻结；冷启动首屏问题（诊断中另发现，38.1%，另行处理）；不做 release 构建对比（M3 再加签名/混淆，避免掩盖真实问题）。

## 四、当前进展

- ✅ 静态分析（含对 2026-09-27 首版交接文档的勘误）：见 [诊断报告.md](诊断报告.md) §2/§3；
- ✅ 真机取证（A/B/C/F/S 全部场景 + 隔离实验）：见诊断报告 §5；
- ✅ **修复实施（P0 + P1，2026-09-27 获用户授权）**：
  - **P0 下拉框**：`RouteSelector.kt` 重写为内联展开（去 Popup 窗口）+ 单一展开源 + options `remember` 稳定引用 → janky **27~38% → 0.45~0.51%**（详见报告 §5.4）；
  - **P1 1Hz 更新**：UI 侧 `monitorStateStable` 拆流（剔 `elapsedSec`/`vib`/`h`/`measuredHz`）+ `elapsedSecFlow` 独立成流 + 订阅下沉 + 秒表原生 TextView；服务侧（已授权）两路 1Hz 上报合一 + 常驻通知内容签名去重 → 静止 41.7% → **25~30%**（残余为秒表走字）、滑动 6.6% → **4.8%**；
  - 功能回归全通过；`gradlew test` 54 项全绿；算法路径零改动；已 `adb install -r` 装机。
- ⬜ **待用户主观验收**：「滑动 / 互切是否不再卡」；残余秒表 1Hz 帧如需进一步降可评估降频（报告 §6 末）。

## 五、约束与红线（诊断期与修复期同样有效）

1. **禁止改动算法路径**：`core/fsm/`、`core/feature/`、`core/model/TuningConfig.kt`（含任何阈值）、`platform/sensor/SensorCollector.kt`、`MonitorService` 的监测循环；
2. **禁止卸载 App / 清除 App 数据 / 手动删 `logs/` 内文件**；装机只允许 `adb install -r`；
3. **禁止改已定稿的系统级配置**：通知渠道属性、前台服务类型 `specialUse`、包名、权限清单；
4. 任何改动完成后自检：`git diff --stat` 确认第 1 条路径零改动 + `gradlew test` **54 项全绿**，不通过不得装机；
5. 涉及 `MonitorService` **UI 上报部分**（`updateOngoing` / ticker，非监测循环本身）的修复，动手前必须获得用户明确同意。
