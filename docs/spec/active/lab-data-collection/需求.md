# 实验室数据采集（通勤标定与判据裁决）

> 跨期背景见 [`../../需求与方案.md`](../../需求与方案.md)；本文件只写本需求。
> 触发背景：2026-09-27「扔垃圾」误报根因分析（`FINDINGS.md`，仓库外分析目录）确认三个结构性漏洞 + **全库没有任何真实乘车数据**（`vibRunTh/vibStopTh` 按手摇标的，真实车厢基线未知）。本需求为采集而立，不做任何算法修改。

## 一、要解决的问题

1. **缺真实乘车数据**：现有 10+ 会话全部是手摇 / 静置 / 走路，没有一段「gyro 低 + vib 中等、持续 ≥30s」的真实乘车形态。`gait-discrimination` 标定与 `vibRunTh/vibStopTh` 重标全部被它阻塞；
2. **步态判据缺走路正样本**（楼下走路一段不足以定阈值，需要奔跑 / 楼梯 / 车厢走动等形态）；
3. **「定位能否进主链路」悬而未决**：与其争论，不如让明天一趟通勤实测回答——定位在地面 / 站厅 / 站台 / 隧道各丢成什么样、恢复要多久、`getSpeed()` 与步态是否互证。**采集数据 → 离线分析 → 再定架构**。

## 二、目标

一次出行（明早通勤）同时完成三件事：① `gait-discrimination` 标定取数；② `vibRunTh/vibStopTh` 真实车厢基线重标取数；③ 定位可用性裁决取证。**采集与现有监测并行**，互不干扰。

## 三、非目标（红线，明确不做）

- **不改任何算法路径**：`core/fsm/`、`core/feature/`、`TuningConfig.kt`、`SensorCollector.kt`、`MonitorService` 监测循环零改动（红线期间 `TuningConfig` 也零改动，采集参数不进去，写在 Lab 自己的常量里）；
- **不进入任何正式功能**：本需求全部代码是旁路调试工具，分析完成后整体下线（见「下线方式」）；
- **不申请定位权限用于主功能**：本需求期间权限清单临时新增，硬性规则 3 的例外以「仅调试采集用途」形式记录在案，下线时一并移除。

## 四、场景清单（用户 2026-09-27 晚确认）

走路、奔跑、车厢里玩手机（小幅度晃动）、上下楼梯（用户提出）+ 补充：站台静立等车、扶梯上站定、站姿乘车、车厢内走动、换乘通道串联段。**户外段（出门→进站口）是金标准**：有 GPS 时 `getSpeed()>0` = 「在走」的地面真值，可做有监督标定。

**场景切换点用通知「📍标记」按钮记录**（用户选定）：Lab 常驻通知放一个标记按钮，切换时按一下（短震确认），写入 `lab_events` 流。

## 五、采集数据面

### 必采（全开）
| 流 | 传感器 / 来源 | 频率 | CSV 列 |
|---|---|---|---|
| `lab_imu` | 加速度计 + 线性加速度 + 陀螺仪（三流分别落行，各自时间戳） | 各 ~50 Hz | t_ms,utc_ms,stream,ax,ay,az |
| `lab_baro` | TYPE_PRESSURE | ~5 Hz | t_ms,utc_ms,pressure,alt_m |
| `lab_light` | TYPE_LIGHT + TYPE_PROXIMITY | ~5 Hz | t_ms,utc_ms,light_lx,prox |
| `lab_loc` | FusedLocationProvider（GPS+网络融合，callback 时触发） | 1 Hz 请求 + 全部回调 | t_ms,utc_ms,lat,lon,accuracy,speed,bearing,altitude,provider |
| `lab_gnss` | GnssStatus.Callback（卫星数 / C/N₀） | 事件驱动（≥1s 节流） | t_ms,utc_ms,sat_total,sat_used,cn0_mean,cn0_max |
| `lab_steps` | TYPE_STEP_DETECTOR + TYPE_STEP_COUNTER | 事件驱动 | t_ms,utc_ms,detector,counter_total |
| `lab_events` | 手动 📍标记 + 服务生命周期事件 | 手动 | t_ms,utc_ms,type,detail |

### 精简合并（实现折中）
加速度计 / 线性加速度 / 陀螺仪**不合并成一行**（三个传感器回调时刻不同，合并会重蹈「陀螺仪相位差」覆辙）——每流独立落行，`stream` 列区分（`accel`/`lin`/`gyro`）。磁力计 + 旋转矢量也进 `lab_imu`（stream 列复用），成本近零。

### 电话状态（用户选开）
蜂窝信号强度：`READ_PHONE_STATE` 权限 + SignalStrength 轮询（5 s 一行，`lab_cell` 流：dbm / level）。

### 文件与容量
- 路径 `logs/lab_<yyyyMMdd_HHmmss>/` 独立子目录（`CsvSessionScanner` 只认 `sensor_/events_/_meta` 三件套，**天然不会被现有保留策略误删**；Lab 自带独立保留策略：最多 3 次采集、每次保留 7 天）；
- 体量：imu 3~5 流 × 50 Hz ≈ 200 行/s × ~120 字节 ≈ **20~25 MB/小时**，其余流 <1 MB/小时。1.5h 通勤 ≈ 35 MB，远在 `retentionMaxMb=200` 之外（Lab 有自己的目录与策略，不占监测 CSV 配额）。

## 六、架构（与主链路完全隔离）

```
platform/lab/
├── LabCollectorService.kt   前台服务（specialUse，subtype=lab_collection），
│                            首行 startForeground；生命周期与 MonitorService 完全独立
├── LabRecorder.kt          多文件写入：每流一个文件，Channel 队列 + 独立 IO scope
│                            （镜像 CsvRecorder 设计：表头同步写 + append + 队满丢弃计数）
├── LabNotifications.kt     Lab 专用通知渠道 lab_ongoing（LOW IMPORTANCE，新渠道，不动三定稿渠道）
├── LabActionReceiver.kt    动态注册（RECEIVER_NOT_EXPORTED）：📍标记 / 停止
├── LabHolder.kt            采集状态单一来源（mirror SessionHolder；仅 LabCollectorService 写）
└── LabStarter.kt           启动入口（mirror MonitorStarter：catch FGS 异常，可见反馈）
core/lab/LabFiles.kt        纯 Kotlin：lab 目录命名/识别 + Lab 保留策略选择逻辑（JVM 可测）
ui/LabCard.kt              调试 Tab 内「实验室采集」卡片：权限请求 + 开始/停止 + 实时状态
```

**每流采集器**在 LabCollectorService 内以 listener / callback 实现，全部注册到独立 HandlerThread；`lab_loc` 用 FusedLocationProvider 时长 5 s 的快速更新（`PRIORITY_HIGH_ACCURACY`），停止时必须 `removeLocationUpdates`（系统级约束：应用切后台 30 s 内不停止会自动静默停止回调）。

### 权限模型（全部只服务于采集）
| 权限 | 用途 | 运行时请求 |
|---|---|---|
| `ACCESS_FINE_LOCATION`（含 COARSE） | 位置流 + GNSS 状态 | LabCard 点「开始」时请求 |
| `ACTIVITY_RECOGNITION` | 计步器 | 同上 |
| `READ_PHONE_STATE` | 蜂窝信号 | 同上 |
| 已有 | 传感器类无需权限 | — |

授权策略：**逐项请求，拒绝即降级**——被拒的流不写文件，其余流照常；LabCard 显示「已授权流 / 总流」。主功能（监测）**不读这些权限**，代码路径零交集。

## 七、验收标准

1. **单测**：`LabFilesTest` —— lab 目录识别（lab_ 前缀、stamp 提取）、保留策略（3 次 / 7 天 / active 保护）、与 `CsvSessionScanner` 不冲突（lab 文件不会被判为监测会话）；
2. **构建**：`gradlew test :app:assembleDebug` 全绿，算法路径零改动（`git diff --stat` 核对）；
3. **真机**（今晚装机后 5 分钟自检，用户执行）：
   - 调试 Tab → 「实验室采集」开始 → 常驻通知出现 → 权限弹窗三项全授；
   - 📍 标记按钮按下有短震、`lab_events` 有行；
   - 放口袋走两分钟 → 停止 → `adb pull logs/`：7+ 个 CSV 文件齐全、行数非零、`lab_imu` ≈ 250 行/分钟以上；
4. **明日通勤正式采集**（用户执行，见下节清单）→ 回传数据质量复核（各流时间对齐、GPS 段/隧道段覆盖）。

## 八、明日操作清单（给用户，装机后贴走）

1. **今晚**：`adb install -r` 后打开 App → 调试 Tab → 实验室采集 → 「开始」→ 三项权限全部允许 → 放口袋走 2 分钟 → 试按一两条「标记」→ 停止 → 电脑拉一把数据做 5 分钟自检；
2. **明早出门前**（进站前完成）：
   - App 正常路线选好，**记录 CSV 已打开**（设置 Tab，标定要用）；
   - 调试 Tab → 实验室采集 → **开始采集**（权限已授过，不会再弹）；
   - 通知栏出现「实验室数据采集」即成功；
   - 正常「开始监测」（或磁贴），两者并行互不影响；
3. **行程中：场景清单逐项标记**——App 内 LabCard 把全部场景分 5 组列出（地面 / 站厅通道 / 站台 / 乘车 / 其他，共 18 项），**到达新场景时点对应行的「标记」**：
   - 语义 =「进入该场景」：两次标记之间自动归上一个场景，**单次点按即可**，无需起止配对；
   - 每行右侧 ×N 是已标次数，方便核对漏项；当前场景前有 ▶，通知栏同步显示「当前：场景名」；
   - 记不住 / 来不及：通知栏「📍标记」按钮做无场景兜底（落 `generic`）；光强/气压/步数/定位事后可辅助对段；
   - 覆盖优先级：**乘车四项（坐玩手机 / 静坐 / 站姿 / 车厢走动）+ 扶梯 + 站台静立** 是判据设计的最值钱样本；地面段（走路/奔跑/楼梯/站定）是步态标定的金标准；
4. **到站后**：结束监测 + 停止采集（通知按钮），说一句「录好了」由 AI 拉数据。

## 十一、数据回传结论（2026-09-28，采集目标全部完成）

早通勤（6 号线 12 站 + 4 号线 2 站 + 22 个场景标记）数据回传，三个采集目标全部有结论：

1. **vibRunTh/vibStopTh 真实车厢重标**：✅ 完成。巡航 vib p25≈0.10 / p50≈0.135，停站 p50≈0.074
   （开门人群噪声 p90≈0.131）；`vibRunTh 0.25→0.10`、`vibStopTh 0.08→0.085` 已写入 v2
   （见 `gait-discrimination/需求.md` 第八节）；
2. **步态标定取数**：✅ 已采。走路（室内/户外/楼梯/站厅/站台）+ 乘车（站姿/坐姿玩手机/车厢走动）
   全场景样本在 `lab_20260928_080252/`，陀螺走路 1.8~3.4 rad/s vs 乘车 p50 0.18~0.44——
   供步频谱峰判据（尚未实施）使用；
3. **定位可用性裁决**：❌ **定位不可用，方向关闭**。隧道内 GNSS 卫星可见但定位冻结在进站前；
   FusedLocationProvider 只剩 network 档（精度 500 m、坐标冻结）——连「上车站/出站身份确认」
   都撑不起，维持 2026-09-27 架构裁决（不推倒、不引入定位）。

**采集使命完成，本需求进入待下线状态**（下线方式见「九」：UI 移除 + 三权限回收 + 渠道保留待删）。
